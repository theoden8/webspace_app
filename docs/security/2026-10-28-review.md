# Security review 2026-10-28

**Scope:** the real screen sharing branch, PR #835 (`claude/keen-fermi-iub43y`):
Android's `MediaProjection` share and the microphone permission fix, the macOS
`SCContentSharingPicker` share, the Linux desktop-portal share, and the Dart
bridge, shim, grants and lifecycle they share. A diff review: surfaces the
branch does not touch were read only where a path from it led into them.
**Method:** five surface reviewers (bridge and shim; Android native; macOS
native; Linux native; settings, grants and persistence), each given the threat
model in [README.md](README.md) and reading source only, the Linux one with
AddressSanitizer reproducers. Every candidate was then re-derived from source
by the lead reviewer: the plugin's wrapper construction for SEC-029, the SDK's
`ScreenCaptureKit.swiftinterface` for the macOS build break, the manifest and
`provideFlutterEngine` for SEC-033, and the reviewer's race reproducer run
against both the old and the fixed `take()` for SEC-037. Confidence is the
verifier's.

## High

### SEC-029: A share outlives its document

* File: `lib/services/webview.dart` (`viewKey`, `onLoadStart`), `lib/services/page_handlers.dart` (the share's owner)
* Confidence: 9 (the plugin's `onWebViewCreated` gets `controllerFromPlatform(_controller)`, a new wrapper; every event callback gets `_controllerFromPlatform`, another one; `PagePhases` already keys on `controller.platform` for this reason)
* Description: the share's owner was keyed by `identityHashCode` of the
  `InAppWebViewController` wrapper `onWebViewCreated` received, and
  `onLoadStart` computed the key from its own wrapper, so `endView` never
  matched. The next document in the same webview (a nested screen navigated in
  place, a later page of the site, a redirect target the site keeps) read the
  live share by calling `webScreenShareFrame` directly, and its pulls kept the
  idle watchdog away. PASSKEY-015's cancel used the same key and was dead too.
* Fix: `ViewKey` (`lib/services/view_key.dart`), an extension type made only
  from `controller.platform`, keys the share and the passkey gate; the share
  also ends when its view unmounts. `test/screen_share_test.dart` gives two
  wrappers over one platform controller, as the plugin does.

## Medium

### SEC-030: In a hosted tab a share outlives its slot leaving the screen

* File: `lib/services/page_handlers.dart` (owner's site is `config.posture.siteId`), `lib/web_view_model.dart` (`stopRealCapture`, `disposeWebView` end the slot's `siteId`)
* Confidence: 8
* Description: a hosted tab (LIR-018) runs as its host, so the share's owner was
  the host's id while the deactivation stop ended the slot's. A page that
  called the handlers directly (no shim track to stop) kept pulling frames of
  whatever replaced it on screen.
* Fix: every frame pull asks the slot's own on-screen gate
  (`grants.isSiteActive`) before and after it waits, and ends the share when
  the slot is off screen; a start the user said yes to after the slot left is
  stopped. The gate is the one the start already used, so it holds whatever
  site the page runs as.

### SEC-031: A popup runs under the site's `real` grant

* File: `lib/services/popup_webview.dart` (handlers registered with the parent's config), `lib/services/webview.dart` (`onCreateWindow`)
* Confidence: 8
* Description: popups registered their capture handlers with the opener's
  `PersistedGrantStore`. Their top document is the main frame, so a captcha or
  sign-in popup page started a real share under the site's grant with only the
  system's prompt in the way, and an Allow given there was saved as the site's
  `real`. Combined with SEC-042, an ad iframe could open such a popup on HTML it
  hosts. The same path is 2026-09-10 A-4 for the camera.
* Fix: a popup answers from an `InMemoryGrantStore` seeded from the opener's
  nested posture, on screen while the opener's slot is; its share ends with its
  documents and its view. Gated in `page_bridge_authority.test.js` (SHARE-014).

### SEC-032: A foreign tab runs under the opener's saved `real` grant

* File: `lib/web_view_model.dart` (`getWebView`)
* Confidence: 7
* Description: a foreign tab (LIR-034, the default with routing off) runs
  another domain's pages as the opener, and took the opener's posture and
  persisted store whole, where LIR-034 says it runs as a nested screen of the
  opener's does.
* Fix: a foreign tab's webview takes `forNested()` and an in-memory store.
  Gated in `page_bridge_authority.test.js` (LIR-034).

### SEC-033: Android: a second app instance reads another's share

* File: `android/.../ScreenSharePlugin.kt` (process-global `ScreenShareSession`), `MainActivity` (`singleTop`, `SEND` filter, one engine per activity)
* Confidence: 6
* Description: a share sheet from another app starts a second `MainActivity`
  in that app's task, with its own engine and Dart side. Native share state is
  the process's, so a page in one engine pulled the frames of a share the user
  started for a site in the other.
* Fix: a share belongs to the plugin that started it: only it reads the
  frames, stops the share or hears that it ended. Gated in
  `test/js/screen_share_native_owner.test.js`.

### SEC-037: Linux: the chunk offset is read twice

* File: `linux/screen_share.cc` (`Stream::take`)
* Confidence: 8 (ASan heap-buffer-overflow and a plain `-O3` segfault in the reviewer's unit reproducer; reproduced here against the old code, and 200,000 racing rounds clean against the fixed one)
* Description: `spa_chunk` lives in memory the producer maps read-write; the
  offset checked against `maxsize` was read again to address the copy, so a
  producer changing it in between made the runner read outside the buffer and
  JPEG-encode what it found for the page.
* Fix: each chunk field is one atomic load into a local, checked and used;
  the negotiated size is checked before it is stored. Gated in
  `test/js/screen_share_linux_chunk.test.js`.

## Low

### SEC-034: Android: a share outlives its engine

* Confidence: 7. The activity destroyed (swiped away, back on Android 11 and
  lower, recreated) took the Dart side with it; the foreground service kept
  the projection running with nothing to end it. *Fix:* `ScreenSharePlugin.dispose`
  in `cleanUpFlutterEngine`, `onTaskRemoved` ends the share; a start abandoned
  after the user's yes enters the foreground before it ends, since a service
  started for the foreground that stops first crashes the app.

### SEC-035: A frame number above 2^31

* Confidence: 8 for the mechanism. The page's `after` reached Kotlin as a
  `Long`, `argument<Int>` threw, Dart read the error as an ended share and
  forgot it without stopping native: the capture ran on with nothing owning
  it. *Fix:* the handler takes 0..2^31-1 only, Kotlin reads a `Number`, and
  Dart stops native whenever it reads an ended answer.

### SEC-036: A share starts from the background

* Confidence: 5. A site with a stored `real` that keeps running in the
  background could call the start: on Android 7 to 9 the capture prompt
  appeared over another app, on 10 and later it was blocked and never
  answered, refusing every later share. *Fix:* `ScreenShare.start` refuses
  unless the app is in front, and Android's plugin checks that its activity
  is resumed.

### SEC-038: Linux: a session handle the portal did not make

* Confidence: 9. A `session_handle` that was not an object path crashed in
  `g_variant_new`; any other path was followed. Only the owner of
  `org.freedesktop.portal.Desktop` can answer, and xdg-desktop-portal lets an
  unsandboxed process replace it. *Fix:* the handle must be the one the portal
  makes from this session's token. In `check.sh`'s hostile cases, with a planted
  mistake.

### SEC-039: Linux: the fd index is trusted

* Confidence: 9. An index past the list hit a NULL `GError`; -1 duplicated
  whatever integer sat before the list. *Fix:* the index is range-checked
  first. In `check.sh`'s hostile cases.

### SEC-040: macOS: a start answered by another pick's stream

* Confidence: 3. The start's completion checked that some start was pending,
  not which, so two picks within one start's latency could answer a later
  start with the earlier pick. *Fix:* each start carries a token; only its
  first pick builds a stream and only that stream answers it.

### SEC-041: Archive sections keep `real` grants and scripts (open)

* File: `lib/services/archive.dart` (`importSections`), `lib/controllers/archive_controller.dart` (`_materialise`, `_moveOutHeld`)
* Confidence: 7. A section restored from a backup is written as it came:
  `sanitizeImportedSites` runs only on the app-tier import. Moving such a site
  out of the archive makes its `real` grants (camera, microphone and now the
  screen) and enabled user scripts live without the user agreeing on this
  device. Predates #835 for every kind but the screen. *Proposed fix:* one
  map-level sanitiser used by both import paths, run on each section's sites
  before `_writeState`.

### SEC-042: Any `googleapis.com` `/recaptcha/` path is a captcha (open)

* File: `lib/services/webview.dart` (`_recaptchaDomains`, `isCaptchaChallenge`)
* Confidence: 6. `storage.googleapis.com/<bucket>/recaptcha/...` serves
  user-uploaded HTML, and opens as a "Verification" popup from any frame. The
  SEC-024 class in a third place; with SEC-031 fixed it no longer reaches a
  grant. *Proposed fix:* recognise reCAPTCHA only on `www.google.com`,
  `www.gstatic.com` and `www.recaptcha.net`.

### SEC-043: A site's grant follows its webview, not the origin (open)

* Confidence: 6. The site's own webview answers from the site's grant
  whatever its top document is (a redirect target it keeps, a later page),
  and a nested screen's answer serves its later pages. SHARE-014, CAM-005 and
  MIC-005 allow this within one surface; the threat model says a grant
  belongs to the origin named. A product decision: bind an answer to the
  origin that gave it, or require the top URL to be within the site's claim
  before a persisted `real` is used.

## Functional (not attacker-triggerable), fixed in #835

- **macOS did not build:** `SCContentSharingPickerConfiguration` is a Swift
  struct, so `let configuration` could not be mutated. The type-check stub
  modelled it as a class; it now carries the SDK's Swift-facing shapes
  (struct, `maximumStreamCount: Int?`, the picker's unavailable `init`) and
  catches the `let` when planted.
- **macOS picker wedge:** `maximumStreamCount = 1` with a stop that completes
  later could make the next `present()` show nothing, leaving the start
  unanswered and every later share refused until relaunch. The count is unset,
  and a stop or an owner that goes takes the pending start down
  (`ScreenShare._cancelPending`).
- **macOS first frame dropped:** only `.complete` frames were kept; the first
  frame a stream sends is `.started`, so a still window showed nothing.
- **macOS stopped stream retained:** the output is removed before the stop.
- **Android:** a start the service found without consent was never answered;
  a display that failed to build with `IllegalStateException` leaked its
  thread and reader.

## Appendix: below the bar, leads and limits

- **2026-09-10 A-6 now covers the screen:** Android Auto Backup and
  device-to-device transfer carry a stored `real` screen grant to a new
  device. Still gated there by the system's prompt.
- **Linux, only the picked node:** holds because the portal hands over a
  remote restricted to it; given an unrestricted remote, WirePlumber relinked
  a vanished node's stream to another source. The stream now sets
  `node.dont-reconnect`.
- **Linux, producer memfds (unverified, 3):** a producer allocating its own
  memfd shorter than `maxsize`, or truncating it later, would SIGBUS the copy.
  A fix would `fstat` and require `F_SEAL_SHRINK`.
- **Same-origin subframes** call `top.flutter_inappwebview` and are reported
  as the main frame; they can script the top document anyway. SHARE-005's
  "stricter than `self`" cannot hold for them: a wording fix.
- **Android leads (4):** a password typed while a share runs shows its last
  character briefly (Flutter `obscureText`); whether Chromium lists more audio
  inputs with `MODIFY_AUDIO_SETTINGS`; with notifications denied on Android
  13+, the share's notification and its Stop are absent though the system's
  indicator shows.
- **Response landing in a new document:** a handler's reply is written into
  whichever main-frame document is current when it lands. SEC-029's fix ends
  the share at the navigation's start, before a new document can ask; a
  document scope check on the frame handler would close what remains.

## Verified safe

- **Frames and workers:** all three share handlers refuse a subframe; the
  request handler refuses `ShimFrames.top` kinds in one; `isMainFrame` comes
  from each frame's own bridge preamble behind the bridge secret; workers have
  no bridge and the worker shim carries no screen script.
- **The owner and the page's values:** the owner is never page-controlled; a
  `real` forged in the page is asked again in Dart; sizes are clamped to
  1..8192 and fps to 1..15 by pattern, `maxLongSide` is Dart's; the
  notification text is the webview URL's host in a localized string.
- **Where `real` must not reach:** archive tier (folded to block, and moving
  into the archive disposes the webview, which ends the share); import
  (`withoutRealGrants`); QR (captures withheld); nested screens; headless
  wake checks (no grants, no handlers, no shims); iOS and macOS before 14
  (refused in the start handler and the shim). Older builds read `real` as
  `ask`.
- **ARCH-001 / ARCH-006:** no new pref or persisted state; no native side
  writes to disk; the Linux portal is asked for no `persist_mode`.
- **Android:** the service is not exported; its PendingIntents are explicit
  and immutable; consent is used once; the foreground service is entered with
  type `mediaProjection` before `getMediaProjection`, and the callback is
  registered before the virtual display; every `Result` is answered once; the
  capture thread's state is confined and frames cross as immutable posts;
  `MODIFY_AUDIO_SETTINGS` is a normal permission no app code uses.
- **macOS:** the sandbox and entitlements are unchanged and none is needed;
  every macOS 14 API sits behind availability, ScreenCaptureKit is weak-linked;
  state is main-queue only; no frame of an ended share is delivered.
- **Linux:** a spoofed `Response` or `Session.Closed` from another bus client
  is dropped (sender match, GLib with the CVE-2024-34397 fix); a second
  `Response` is ignored; a cancelled dialog is closed with `Request.Close`;
  async callbacks after an end never touch freed state (Host destroyed at nine
  points under ASan, 20 rounds of start/frame/stop churn clean); every
  `FlMethodCall` is answered once; PipeWire state is touched only on its thread
  or under its loop's lock.
