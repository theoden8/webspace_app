# Security review 2026-09-10

**Scope:** whole application at `74cefb5` (master). Not a diff review: the branch had no
pending changes, so the review covered every attack surface listed in
[README.md](README.md).
**Method:** eight surface reviewers, then one independent verifier per candidate
(44 candidates). Only findings whose verifier scored confidence 8 or higher, or that
were re-checked by hand against source, are in the main list. Everything else is in
the appendices with its score, so nothing found is lost.
**Fork:** the pinned flutter_inappwebview fork was read from a shallow clone of
`v6.2.0-beta.3-privacy-v6` where noted; where the clone was unavailable the verdict
rests on the app's own comments and specs and says so.

Every fix below keeps the user experience intact. Where a fix adds a prompt or changes
a visible default it says so explicitly; the rest are invisible.

### Where a fix departs from the suggestion

- **SEC-001**: probed from Dart (`appleOsMeetsFloor` over
  `Platform.operatingSystemVersion`, `lib/platform/apple_os_floor.dart`) rather
  than a native `#available` channel; below the floor the proxy controls are
  hidden and a persisted non-DEFAULT proxy fails closed. No pbxproj/Podfile
  structural test: the runtime probe no longer assumes the floors agree.
- **SEC-006**: guarded in the Dart tier
  (`test/anti_fingerprinting_seed_opacity_test.dart` reads the script source
  the worker payload copies); no browser-tier `createObjectURL` capture added.
- **SEC-011**: the TLS hop is a `connectionFactory` handing dart:io a
  `SecureSocket` to the proxy; dart:io nests the origin's TLS through the
  tunnel, verified against real sockets in
  `test/outbound_https_proxy_hop_test.dart` (a plain listener sees only a
  ClientHello; a TLS CONNECT proxy sees the credentials inside the session).
- **SEC-015**: a same-origin iframe keeps the fix (the engine's default `'self'`
  allowlist); only a cross-origin frame is refused.
- **SEC-016**: images are re-encoded (JPEG stays JPEG, else PNG); ISO-BMFF
  `udta`/`meta`/`uuid` boxes are blanked in place; MP3 ID3 tags are cut.
  webm, ogg, wav, flac, aac and weba are delivered as picked (CAM-015 says
  so).
- **SEC-019**: compound queries are rewritten and delegated; the stylesheet
  `@media` leak stays and is recorded as a residual under ETP-010.
- **SEC-020**: the review names the title and the synthesised address; the
  sender package and byte count were not threaded through
  `DispatchCreateSiteFromHtml`.
- **SEC-027**: bounded, not eliminated; the residual probability is stated in
  the archive spec's Limitations.
- **SEC-025**: `toDateString` and `toTimeString` are rebuilt; the `Date()`
  call form is left as a stated gap under LOC-003.

## High

### SEC-001: Container and proxy support decided at build time; iOS 15/16 and macOS 10.15 to 13 share one data store

* File: `lib/services/container_native.dart:156-173`; `lib/main.dart:4814`; `lib/services/webview.dart:1812-1816`, `503-512`, `1842-1844`
* Spec contradicted: per-site-containers spec lines 14-17 and 35-36; ip-leakage LEAK-003; `docs/releasing-macos.md` "Known limits"
* Confidence: 8
* Description: `_ContainerNative.isSupported()` returns the fork's synchronous
  `ContainerController.isClassSupported(platform:)`, a static platform-name list with no
  runtime probe (the repo's own audit at `docs/upstream/flutter-inappwebview-audit.md:199-202`
  says so). The comment justifies it with "iOS 17 / macOS 14 are our runtime floor", but the
  floors are `IPHONEOS_DEPLOYMENT_TARGET = 15.0` (`ios/Runner.xcodeproj/project.pbxproj:575`,
  `ios/Podfile:3`) and `MACOSX_DEPLOYMENT_TARGET = 10.15` (`macos/Runner.xcodeproj/project.pbxproj:655`,
  `macos/Podfile:1`). No `#available` or `isOperatingSystemAtLeast` probe exists under `ios/` or
  `macos/`. On an OS below the floor `_useContainers` is true, so the legacy same-base-domain
  mutex and capture-nuke-restore are switched off (`main.dart:4042-4058`), every non-incognito
  site is handed a `containerId` the fork ignores below `#available(iOS 17, macOS 14)`, and all
  sites land on the default `WKWebsiteDataStore`. `PlatformInfo.initialize` reports proxy
  support unconditionally, and `proxyUnavailable` is only raised for a malformed address, so a
  per-site SOCKS5/HTTP proxy is silently dropped too.
* Exploit: user on an iPhone X (iOS 16) or 2017 Mac (macOS 13) installs the store build. Two
  sites on one domain overwrite each other's session; a third-party script embedded on two
  sites reads one cookie jar; a proxied site loads over the device IP while settings show the
  proxy applied.
* Fix (invisible on iOS 17+/macOS 14+): add a `MethodChannel` in `ios/Runner` and `macos/Runner`
  returning `if #available(iOS 17.0, macOS 14.0, *) { true } else { false }` and use it in
  `isSupported()` and `PlatformInfo.initialize`; below the floor the legacy engine runs as the
  spec already describes, and a persisted non-DEFAULT proxy becomes `proxyUnavailable`
  (blank load) instead of a direct load. Alternative: raise the deployment targets to 17.0 and
  14.0. Either way add a structural test that the pbxproj/Podfile floors agree with the
  build-time assumption, and correct the two docs.

### SEC-002: Android container mode binds incognito and archive-tier sites to the persistent default profile

* File: `lib/services/webview.dart:1801-1816`; `lib/web_view_model.dart:778`, `2289-2312`; fork `InAppWebView.java:291-296`, `702-716`
* Spec contradicted: archive ARCH-006/ARCH-007 ("nothing survives a session", opaque container ids); per-site-containers incognito ephemerality
* Confidence: 9 (fork source read)
* Description: `_bindingFor` sets `containerId = null` whenever `config.incognito` is true, and
  the comment assumes this "sends the incognito site to the default (non-persistent-semantics)
  store on Android". It does not. The fork's `setIncognito(true)` only calls
  `CookieManager.getInstance().removeAllCookies()`, sets `LOAD_NO_CACHE` and clears history;
  DOM storage stays on and the androidx default profile is persistent under
  `app_webview/Default/`. Archive-tier sites are forced incognito by `effectiveIncognito`, so on
  Android the ARCH-007 `archiveContainerId` path never binds anything: `_closeArchive` deletes
  containers that were never created (`main.dart:3238-3250`), the startup GC finds no
  `ws-<siteId>` to drop, and the legacy jar clear is skipped under containers
  (`orphan_sweep_engine.dart:462-464`). `_pushPendingArchiveCookies` writes the archive's saved
  login into that shared default jar through the global cookie manager.
* Exploit: (a) open an archive on Android, log in to an archived site, close the archive; its
  cookies, localStorage and IndexedDB remain in cleartext under `app_webview/Default/`.
  (b) While the archive is open, an app-tier incognito site of the same domain shares that jar
  and storage with the archived site. (c) Two app-tier incognito sites of one domain share
  identity and their storage survives restart.
* Fix (invisible): on Android always bind a per-site profile, `ws-<siteId>` for incognito and
  `ws-<archiveContainerId>` for archive-tier, even when `incognito` is true, and rely on the
  existing teardown hooks (startup `onSiteDeleted` for incognito ids, `deleteContainer` in
  `_closeArchive`, `disposeWebView`) to delete it. Keep the `!incognito` gate only on Apple and
  Linux, where the fork supplies an ephemeral store. Add a container-mode test asserting an
  incognito or archive `WebViewConfig` yields a non-null `containerId` on Android.

### SEC-003: Android/Linux apply the proxy override after the first navigation is dispatched

* File: `lib/services/webview.dart:3645-3650`, `1830-1844`, `329-349`; `lib/web_view_model.dart:1667-1674`, `1037-1042`, `1088-1113`; `lib/main.dart:4060-4084`
* Spec contradicted: ip-leakage LEAK-003; proxy PROXY-008
* Confidence: 8
* Description: the platform view is built with `initialUrlRequest` set to the site URL and, on
  Android/Linux, no per-webview proxy. The process-global override is applied only from
  `onControllerCreated` (un-awaited) via `setController()` and `_applyProxySettings()`, after a
  relay bind and probe for credentialed proxies. The app's own comments say the navigation has
  already started by then (`web_view_model.dart:1061`, `1676-1679`). The activation path only
  unloads mismatched siblings and never pre-applies the override; a DEFAULT site clears it. The
  `about:blank` fail-closed branch runs only on exceptions. This is deterministic ordering, not
  a race. Mirror case: a DEFAULT site built while the override still holds another site's
  proxy sends its first request through that proxy.
* Exploit: user is on a DEFAULT site, taps a SOCKS5 site. Chromium resolves and fetches the
  first page direct (DNS, SNI, cookies from the site's container) before Dart sets the
  override. Same on every cold start where the restored site is proxied.
* Fix (invisible, page starts one channel round trip later): in `getWebView` pass
  `deferInitialLoad` on Android/Linux when the effective proxy is non-DEFAULT (the
  `suppressInitialLoad` mechanism at `webview.dart:3465-3468` already exists) and issue the
  first `loadUrl` from `setController()` only after `_applyProxySettings()` returns without
  throwing. Deferring every site on Android/Linux also closes the mirror case.

### SEC-004: "Open in site" nested webview ignores the target site's proxy on Android and Linux

* File: `lib/main.dart:2814-2856`, `2934-2957`; `lib/screens/inappbrowser.dart:368-378`, `440`; `lib/services/webview.dart:298-469`, `1830-1844`
* Spec contradicted: ip-leakage fail-closed; PROXY-008; TOR-008
* Confidence: 8
* Description: `_executeOpenNested` (reached from a share intent, `webspace://open?url=`, a
  stored domain claim with no prompt, or the picker's "Open in [site]") pushes an
  `InAppWebViewScreen` for the chosen site without activating it, and neither it nor the
  nested screen calls `ProxyManager`. The nested config's `proxySettings` is ignored on
  Android/Linux (`_bindingFor` only binds on Apple), so the webview loads through whatever
  override the currently active site left, bound to the proxied site's container. For Tor the
  screen waits for bootstrap and then loads direct.
* Exploit: site "Forum" is behind Tor; the user is viewing a DEFAULT site; a URL shared from
  another app is opened in Forum. The request, carrying Forum's cookies, leaves on the device IP.
* Fix (invisible): in `_executeOpenNested`, when `hostIsAndroid || hostIsLinux` and the target's
  effective proxy differs from the active site's, run the PROXY-008 sequence before `launchUrl`:
  unload `indicesToUnloadForProxyMismatch`, `await ProxyManager().setProxySettings(model.outboundProxySettings)`,
  and do not push the screen if it throws. For Tor, apply inside the `TorUp` callback.

### SEC-005: QR and deep-link site review misses a proxy whose `type` is a JSON string

* File: `lib/main.dart:7991-8002`; `lib/settings/proxy.dart:84-90`; `lib/services/site_settings_qr_codec.dart:173-192`; `android/app/src/main/AndroidManifest.xml:58-63`; `ios/Runner/AppDelegate.swift:141-147`
* Spec contradicted: site-settings-qr QR-008 ("the proxy address is allowed but is named in the review dialog")
* Confidence: 9
* Description: `_confirmQrSiteSettings` shows the proxy line only when `type is int`, but the
  value is applied through `UserProxySettings.fromJson`, whose `_typeFromIndex` also accepts
  numeric strings via `int.tryParse`. The codec strips only `password` and does not type-check
  `type`; nothing between decode and `fromJson` normalises it. So `"type":"1"` passes the
  review with no proxy line and creates a site whose HTTP proxy is the attacker's host, which
  takes precedence over any global proxy. Reachable from a scanned or pasted QR and from the
  exported `webspace://qr/site/...` scheme on Android and iOS. No other reviewed field has this
  divergence: the bool fields throw on non-bool input.
* Exploit: a link `webspace://qr/site/v1/<gzip+b64 of {"initUrl":"https://portal.example","name":"Support Portal","proxySettings":{"type":"1","address":"proxy.attacker.example:8080"}}>`.
  The dialog shows only URL and name. After accept, that site's traffic (real IP, every
  destination host, all plaintext content) transits the attacker's proxy, bypassing a global
  Tor/SOCKS setup.
* Fix (invisible): compute the review from the same decoder the apply path uses:
  `UserProxySettings.fromJson(proxyJson)` and show the line whenever `type != DEFAULT`
  (label Tor for TOR, which closes the sibling `type: 4` gap). As defence in depth, make
  `SiteSettingsQrCodec.decode` return null when `proxySettings.type` is not an `int` in range or
  `address` is not a `String`. Add a codec test with `"type":"1"`.

### SEC-006: Worker shim payload hands the anti-fingerprinting seed to page script

* File: `lib/services/anti_fingerprinting_shim.dart:74-84`, `125-133`; `lib/services/worker_shim.dart:82-83`, `100-104`, `466-469`; `lib/services/webview.dart:2071-2078`, `2364-2373`; `lib/services/launch_nonce.dart:9-12`
* Spec contradicted: tracking-protection ETP-022 (reroll on clear), incognito per-launch reroll, container unlinkability
* Confidence: 9 (reproduced by the reviewer in headless Chromium against the committed fixture)
* Description: the seed is the persistent record id verbatim (`siteId`, `siteId:resetNonce`, or
  `...:launchNonce`) and is embedded as `var SEED = "<seed>"`. `buildWorkerShimScript` copies
  the shim text into a page-side `PAYLOAD`, turns it into a never-revoked `blob:` URL (cached
  in `_url`) and `importScripts` it into every worker, in every frame. Page script obtains the
  payload by overriding `URL.createObjectURL` (resolved at call time) before creating any
  `Worker`, or by fetching the blob URL read from a stack trace inside a worker. The stable
  `siteId` prefix defeats the reroll on "Clear site data" and the incognito per-launch reroll;
  `LaunchNonce.value` is process-wide, so two incognito sites in different containers can link
  themselves to one install and session.
* Exploit: a tracker runs
  `const o=URL.createObjectURL; URL.createObjectURL=b=>{b.text().then(t=>{const m=/var SEED = ("(?:[^"\\]|\\.)*")/.exec(t); if(m) beacon(JSON.parse(m[1]));}); return o.call(URL,b);}; new Worker('/x.js');`
  and stores the `siteId` prefix server-side. After a wipe or relaunch the same prefix returns.
* Fix (invisible): pass an opaque digest to `buildAntiFingerprintingShim`, e.g.
  `sha256('ws-afp:' + seed)` or an HMAC under a per-install secret from `flutter_secure_storage`,
  keeping `computeAntiFingerprintingSeed` as the input so ETP-004/ETP-022 semantics hold. Derive
  the incognito launch component per site (`sha256(launchNonce + siteId)`) so no two containers
  share a suffix. Add a browser-tier regression in `test/browser/worker_realm_escape.test.js`
  that captures the blob via a `createObjectURL` override and asserts no `siteId`-shaped token.

### SEC-007: Nested webview inherits the parent site's `real` camera and microphone grant

* File: `lib/screens/inappbrowser.dart:349-352`; `lib/web_view_model.dart:1433`, `1540`; `lib/services/media_grant_engine.dart:74-76`; `lib/services/camera_decision_engine.dart:61-63`; `lib/services/webview.dart:3739-3790`
* Spec contradicted: web-camera-access CAM-005 and CAM-014; web-microphone-access MIC-005 and the MIC-014 clause "a nested webview decides for itself and persists nothing"
* Confidence: 8
* Description: `InAppWebViewScreen` seeds `_cameraMode`/`_microphoneMode` from
  `widget.cameraMode`/`widget.microphoneMode` with no mapping, and both `launchUrlFunc` call
  sites forward `effectiveCameraMode`/`effectiveMicrophoneMode` unfiltered, including `real`.
  The nested page is the top document of its own webview, so `MediaGrantEngine.decide`
  short-circuits on `settled` and returns `real` for any origin; the shared native
  `onPermissionRequest` grants after the same resolver and the app-level OS permission (already
  held). In-place cross-origin navigation inside the nested screen inherits it too. The URL-bar
  path does not forward the modes, so the two entry points disagree.
* Exploit: user allowed the real microphone on a voice-chat site; an attacker posts a link there;
  the user taps it; `evil.example` in the nested screen calls `getUserMedia({audio:true})` and
  receives the device microphone with no dialog naming it.
* Fix (invisible except in the case the spec already promises a prompt): in
  `_InAppWebViewScreenState.initState` map `CameraAccessMode.real` and `MicrophoneAccessMode.real`
  to `ask` when seeding; keep `block`, `virtual` plus source, and the forced blocks. Add a test
  that a screen constructed with `cameraMode: real` invokes `resolve` on the first request, and
  the scenario under CAM-005/MIC-005.

### SEC-008: Favicon URL cache persists archived sites' URLs into plaintext prefs

* File: `lib/screens/add_site.dart:20-47`, `202-240`; `lib/services/icon_service.dart:102`; `lib/main.dart:3105-3132`, `7520`, `8129`, `8931`, `8984`, `3246-3255`; `lib/screens/webspace_detail.dart:145`
* Spec contradicted: archive ARCH-001 (byte-identical prefs), ARCH-006 (no row for the icon cache)
* Confidence: 9
* Description: `FaviconUrlCache.set` writes `favicon_url_<full initUrl>` (and `favicon_svg_<iconUrl>`
  with the SVG body) to stock SharedPreferences whenever `UnifiedFaviconImage`'s stream
  completes. The widget has no tier input, and archive-tier models are rendered through it by
  the tab strip, drawer grid, edit dialog and webspace detail. `_closeArchive` erases nav state,
  cookies, HTML cache and proxy passwords but not these keys, and nothing else ever removes
  them. The neutrality test never pumps a widget. (The `main.dart:8694` shortcut picker is
  filtered by `!isArchiveTier` and is not a leak path.)
* Exploit: an adversary with a device backup or filesystem image greps
  `FlutterSharedPreferences.xml` for `favicon_url_` and diffs against the active site list:
  every extra URL is an archived site, proving an archive exists and naming its hosts and paths.
* Fix (invisible): add `persist: bool` to `UnifiedFaviconImage`, pass `!model.isArchiveTier` at the
  five render sites, skip both `set` calls and thread the flag into `getSvgContent` so the
  `onSvgContentCached` write is skipped; in `_closeArchive`'s back-erasure loop call
  `FaviconUrlCache.invalidate(m.initUrl)` for each owned site to clean entries from earlier
  builds. Add a favicon row to the ARCH-006 matrix and a widget test asserting no `favicon_` key
  after an open/render/close cycle. Also check whether `ImageCacheService` keeps the icon bitmap
  on disk keyed by the same URL.

### SEC-009: DEFAULT sites inheriting a global Tor proxy are built unproxied while Tor bootstraps and never rebound

* File: `lib/web_view_model.dart:1197-1211`, `1016-1017`, `1319`, `2190-2199`; `lib/screens/inappbrowser.dart:368-369`; `lib/services/webview.dart:1830-1848`, `3466-3467`, `3648-3656`, `4367-4378`; `lib/main.dart:1252-1253`
* Spec contradicted: PROXY-011 (DEFAULT sites inherit global TOR), TOR-008
* Confidence: 8 (severity Medium only because Tor is iOS-only behind developer mode; High once the TOR-013 gate is removed)
* Description: the TOR-008 gate checks the raw per-site type, so a DEFAULT site under a global
  Tor proxy is not gated. `_bindingFor` resolves it through the global, `expandTorProxy` returns
  null while Tor is down, and the data store is created with `proxySettings: null` for the
  widget's lifetime. `proxyUnavailable` only blanks the initial URL; it does not gate
  `renderInitialData`, so a site with HTML caching on renders its snapshot against the live
  `baseUrl` and fetches subresources direct, then reloads. The Tor-Up listener disposes only
  raw-TOR models, so every later `loadUrl` on that tab (URL bar, PAUSE-022 reissue) is direct.
  The comment at `web_view_model.dart:1197-1204` cites PROXY-011 for the opposite of what it says.
* Fix (invisible): gate on `resolveEffectiveProxy(proxySettings, siteId: siteId).type == TOR && !status.isUp`
  in `getWebView` and the nested screen; dispose every model whose effective type is TOR in
  `_onTorStatusChanged`; fold `proxyUnavailable` into `renderInitialData`. Add a test beside
  `test/tor_proxy_resolution_test.dart`.

### SEC-010: Android fail-closed catch tests the raw per-site proxy type

* File: `lib/web_view_model.dart:1088-1114` (line 1107); `lib/services/webview.dart:329-411`, `1842-1844`; `lib/settings/proxy.dart:84-90`; `lib/settings/global_outbound_proxy.dart:112-126`
* Spec contradicted: LEAK-003; PROXY-011 (relay change); TOR-007/TOR-008
* Confidence: 8
* Description: `ProxyManager.setProxySettings` resolves the effective proxy first and throws on
  it (missing or malformed global address, relay bind failure) without clearing any override,
  but the caller blanks the page only when the raw `proxySettings.type != DEFAULT`. A DEFAULT
  site inheriting an unusable global proxy swallows the exception while its initial navigation
  continues direct. Reachable via a credentialed global proxy whose relay fails to bind, a
  backup carrying a non-`host:port` global address (import never validates it), or an iOS
  backup with global TOR imported on Android (`_typeFromIndex(4)` decodes to TOR, the runtime is
  never available, the address is null). The Apple path already uses the effective type.
* Fix (invisible for a working proxy): blank on every throw, or test
  `resolveEffectiveProxy(proxySettings).type != DEFAULT`. Pair with SEC-003 so the blank-out
  precedes the first request. Optionally warn at import when the incoming global proxy is TOR
  and Tor is unavailable.

### SEC-011: Dart-side `HTTPS` proxy type is served as a plaintext hop

* File: `lib/services/outbound_http_io.dart:33-63` (only `connectionFactory` is the SOCKS5 one at 131-188)
* Spec contradicted: proxy spec line 58 ("HTTP CONNECT over TLS to the proxy"); ip-leakage LEAK-008
* Confidence: 8
* Description: `ProxyType.HTTP` and `HTTPS` share one arm: `findProxy` returns `'PROXY host:port'`
  and Basic credentials are added with `addProxyCredentials`. `dart:io` opens a plain TCP socket
  to a `PROXY` directive and writes `CONNECT host:port` plus a proactive `Proxy-Authorization:
  Basic` header before any TLS. The Android relay does `startTls` with hostname verification
  first (`ProxyRelay.kt:423-424`, `464-472`); the Dart seam never got the equivalent. Every

## Appendix C: filtered out (hardening or documented)

- WebRTC `defaultPolicy` under a proxy leaks the device IP via STUN. LEAK-005 documents this as
  an accepted gap and the per-site hint says so. Worth a product decision: resolve
  `defaultPolicy` to `relayOnly` at shim-build time when the effective proxy is non-DEFAULT.
- `MainActivity` has default `taskAffinity` (StrandHogg 1.0 on Android 10 and lower). One-line
  hardening: `android:taskAffinity=""`.
- `ProxyRelayPlugin.kt:35` writes the relay endpoint and proxied destination hosts to logcat at
  INFO in release; the Dart side tags the same lines sensitive. Only `READ_LOGS`/adb can read
  it. Gate on `FLAG_DEBUGGABLE`.
- macOS `AppDelegate.swift`, both `ShareViewController.swift` files, both `ShortcutsPlugin.swift`
  and both `WebSpaceAppIntents.swift` log inbound URLs and site ids in release; the iOS delegate
  wraps the same lines in `#if DEBUG`. Log hygiene.
- Theme shim exposes `window.__originalMatchMedia` and a writable `__appThemePreference`; only
  reveals the OS colour-scheme bit, which CSS can read anyway.
- Timing quantisation covers only `performance.now` and `Date.now`; the other clocks are a
  detectable inconsistency, not an exploitable channel here.

## Verified safe

Paths that were checked and hold, with the line that makes them hold. Skip these next time
unless the cited code changed.

- Archive AEAD: AES-256-GCM, per-seal random nonce, slot-index AAD, Argon2id with a per-install
  salt minted alongside the slot pool; key zeroised on close; no hardcoded keys or salts in
  `lib/` (`archive_crypto.dart`, `archive_storage.dart`). HTML cache, HTML import, nav state and
  block-stats detail all AES-GCM with fresh nonces under keystore-held keys. `LaunchNonce` and
  slot selection use `Random.secure`.
- Exports never carry per-site proxy passwords, Secure cookies, Tor bridge lines, trusted-host
  pins or archive material; `sanitizeImportedSites` disables restored scripts; `siteId` is
  path-safe (`^[A-Za-z0-9_-]{1,128}$`); `FileStore` names are validated; no zip handling.
- `LogService` keeps sensitive entries in a memory ring, prints nothing in release, omits them
  from export; no `print`/`debugPrint` outside it.
- `intent://` fallbacks and `x-safari-*` resolve only to http(s) with a host

- Android: no http(s) VIEW filter; all `PendingIntent`s `FLAG_IMMUTABLE`; `readStreamAsString`

  SOCKS5 uses ATYP=domain (no local DNS); unreachable upstream yields 502, never direct; page
