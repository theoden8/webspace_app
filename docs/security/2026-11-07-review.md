# Security review 2026-11-07

**Scope:** the access policy and its proofs ([policy.md](policy.md)), the
page-reachable notification bridge, and every locked dependency. A hardening
pass, not a branch review: it turned the #888 policy into checked data, proved
what a type or model could, scanned dependencies against OSV, and audited where
each platform's bridge takes a frame's identity.
**Method:** source only. The fork's bridge (`theoden8/flutter_inappwebview`,
pinned in `pubspec.lock`) read for how a handler call's origin and main-frame
flag are produced per platform; dependencies scanned with `osv-scanner` v2.7.0
over every tracked lockfile; each policy rule mapped to its strongest check by
`tool/spec_map.js --policy`.

## Verified safe

- **iOS and macOS bridge identity.** A handler call's origin and main-frame
  flag come from WebKit's `message.frameInfo` (`securityOrigin`,
  `isMainFrame`), which page script cannot set. R2 to R4 rest on this, and it
  holds on these platforms.
- **Shipped dependencies.** `pubspec.lock`, `rust/webspace_adblock/Cargo.lock`
  and `tool/webspace_lints/pubspec.lock` carry no advisory OSV reports. CI now
  fails on a new one (`scripts/osv_scan.sh`, `accepted_advisories.tsv`).

## Medium

### SEC-045: Android and Linux decide a bridge call's frame from the page

* File: the fork's `JavaScriptBridgeInterface` / `JavaScriptBridgeJS` (Android),
  `in_app_webview.cc` / `javascript_bridge_js.h` (Linux). Consumers:
  `lib/services/page_handlers.dart` (`requesterOf`), `lib/services/site_origins.dart`.
* Description: R2, R3 and R4 decide by the origin and main-frame flag that
  reach Dart in `JavaScriptHandlerFunctionData`. On iOS and macOS these come
  from the platform. On Android they are computed by the injected bridge
  script and sent in its serialized payload; on Linux the origin is the
  webview's current top URL (so every frame reports the top document's) and the
  main-frame flag again comes from the script. The only thing separating a
  page's own calls from the app's is a secret constant held in the script's
  closure, minted per webview. Because the identity and the payload are
  produced in the page's own realm, the page's environment can reach them: the
  secret alone does not make the identity trustworthy. So on these two
  platforms the frame identity R2 to R4 rely on is part of the trusted base,
  not something the app enforces.
* Impact: the camera, microphone, location, notification and passkey handlers
  all read this identity (CAM-014, MIC-016, LOC-011, NOTIF-010, PASSKEY-004).
  Where it can be influenced, a frame could present as the top document or as
  the site's own origin. Not reachable on iOS or macOS.
* Fix: take the origin and the main-frame flag from the platform, never from
  the page. The three platforms differ:
  - **iOS/macOS:** already platform-sourced (`WKScriptMessage.frameInfo`). Not
    affected; no change.
  - **Android:** `WebViewCompat.addWebMessageListener` delivers `sourceOrigin`
    and `isMainFrame` from the engine. Route the bridge through it; drop the
    page-supplied values and the secret stops being load-bearing.
  - **Linux (WPE, non-Chromium):** the WebKit GLib script-message signal
    carries no frame info, so identity cannot be attributed. The fix is to
    inject the bridge main-frame-only there, denying subframes a capability by
    absence; a same-origin subframe loses handler access as the cost.
  The change belongs in `theoden8/flutter_inappwebview`. The full
  implementation and the tests it needs are in
  [sec-045-remediation.md](sec-045-remediation.md); tracked as an owed `-` row
  for R4 in [policy_debt.tsv](policy_debt.tsv).

### SEC-048: the SSRF literal guard read IPv4-mapped IPv6 as public

* File: `lib/services/host_resolution.dart` (`isPrivateOrLoopbackHost`).
  Consumers: the user-script fetch (`user_script_service.dart`: `__wsFetch` and
  the script-injection handler), `icon_service.dart`, `media_session_service.dart`,
  `proxy_test_service.dart`.
* Description: this is the literal half of the page-steerable-fetch SSRF guard,
  and the resolving half (`classifyResolvedHost`) judges each resolved address
  with the same function. Its IPv6 branch matched only `::1`, `::` and the
  fc/fd/fe8-b prefixes by string, so it returned false (public) for an
  IPv4-mapped literal (`::ffff:127.0.0.1`, `::ffff:169.254.169.254`,
  `::ffff:10.0.0.1`) and for an expanded loopback (`0:0:0:0:0:0:0:1`). For a
  mapped literal both halves pass even with no proxy, and a dual-stack socket
  routes `::ffff:127.0.0.1` to `127.0.0.1` — a reach past the guard to loopback,
  the LAN, or cloud metadata.
* Impact: on a user-script-enabled site, page JS calling
  `__wsFetch('http://[::ffff:169.254.169.254]/…')` reads the body back (full
  SSRF); the icon and artwork fetchers follow a site-supplied mapped URL with
  no user opt-in (blind SSRF). Gated by the caller, so Medium, not High.
* Fix (parity, per supervisor ruling): `isPrivateOrLoopbackHost` parses the IPv6
  literal into its eight groups (compressed or expanded) and judges one address
  the same way whether it is a literal or a resolved address. It unwraps the
  embedded IPv4 of every v4-in-v6 form — IPv4-mapped (`::ffff:v4`),
  IPv4-compatible (`::v4`), NAT64 (`64:ff9b::/96`, `64:ff9b:1::/48`) and 6to4
  (`2002::/16`) — refuses Teredo (`2001:0000::/32`, obfuscated v4) outright, and
  treats site-local (`fec0::/10`), multicast (`ff00::/8`) and the documentation
  ranges as non-public. Non-canonical numeric IPv4 (one decimal/hex number,
  hex/octal octets, `127.1`) is refused rather than guessed. Pure / sync /
  web-safe. Gated by `test/host_resolution_range_test.dart`.

### SEC-049: the fetch guard does not pin the address it judged

* File: `lib/services/host_resolution.dart` (`classifyOutboundTarget`,
  `classifyResolvedHost`); `lib/services/user_script_service.dart`
  (`_resolvedTargetAllowed`, `_getWithCheckedRedirects`).
* Description: the resolving half resolves a name, judges the address, then hands
  the *name* to `http`'s client, which resolves it again on connect. A record
  that changes between the two lookups (DNS rebinding) lands the connection on an
  address neither half judged — both checks passed on the first answer. The code
  already names this residual in `classifyOutboundTarget`'s doc comment.
* Impact: the same reach as SEC-048 (loopback / LAN / metadata) for a caller who
  controls a short-TTL name's answers; harder to land than a static literal.
* Fix: pin the fetch to the exact address judged — resolve once, judge, connect
  to that address with the `Host` header kept — through the client's connection
  factory or the SOCKS/proxy path. `http` does not expose this today, so it is
  its own change, tracked as its own PR, not folded into SEC-048's.
* Status: open.

## Low

### SEC-046: The notification polyfill carried the site id into every frame

* File: `lib/js/notification_polyfill.js`, `lib/services/notification_polyfill_shim.dart`
* Description: the polyfill, injected in every frame, took the site's id in its
  config and sent it with each `webNotification` call. The handler already
  decides the site from the frame identity and ignored the page's value
  (NOTIF-010), so nothing read it, but it put the id in reach of every frame
  for no purpose.
* Fix: the config and the calls carry no site id. Behaviour is unchanged; the
  handler still names the site. Gated in both tiers
  (`test/js/notification_polyfill_shim.test.js`, `test/notification_polyfill_test.dart`).

### SEC-047: A test-tooling dependency carried a known advisory

* File: `package-lock.json`
* Description: `osv-scanner` reported GHSA-mrhx-c7xc-m3w5 (memory exhaustion
  on an oversized constrained collection) against `zod` 3.25.76 and 4.4.3,
  pulled in by the OpenSpec CLI and by puppeteer's `chromium-bidi`. Test and
  build tooling only; never in a shipped artifact.
* Fix: puppeteer bumped to 25.16 and `zod` deduped to 4.6.7. Two advisories
  remain, both unreachable test tooling, both accepted with their reason in
  `accepted_advisories.tsv`: `minimatch` via eslint (our own config's globs
  only) and `nanoid` via `cld3-asm` (called as `nanoid(45)` only).

### SEC-050: the media-session artwork fetch followed redirects past the guard

* File: `lib/services/media_session_service.dart` (`_fetchArtwork`). Found
  auditing the four page-steerable fetchers for redirect handling; the
  user-script (`_getWithCheckedRedirects`) and icon (`_readPageLinked`) fetchers
  already re-judge each hop, `proxy_test_service` does not follow redirects at
  all, and this one did neither.
* Description: the artwork URL comes from page JS (the media-session shim runs in
  every frame), and `_fetchArtwork` guarded the *initial* URL
  (`isPrivateOrLoopbackHost` + `classifyOutboundTarget`) but then issued the GET
  with `http.Client.get`, whose request follows redirects transparently
  (`IOClient` honours `followRedirects`, default true). The direct client's
  `connectionFactory` refuses only onion per connection, not private ranges, so a
  `302 Location: http://169.254.169.254/…` from a public host was followed and the
  GET landed on the metadata / LAN / loopback endpoint.
* Impact: blind SSRF. The fetched bytes become the notification artwork, not a
  value returned to page JS, so the page cannot read the response; the request
  still lands on the internal host. Gated by the media-session shim and requiring
  an attacker-controlled redirecting public host, so Low.
* Fix: follow redirects by hand with the client's own following off, running
  every `Location` back through the same host guard before the next hop, capping
  the body and refusing an https→http downgrade. Gated by
  `test/media_session_service_test.dart` (a redirect into the LAN is refused and
  never requested; a redirect to another routable host is followed; a downgrade
  is refused).
* Debt (one owner): the per-hop redirect re-check now has three near-copies
  (user-script, icon, media-session) and the redirect-status predicate four. One
  owner would be a guarded connection factory on the direct client that resolves
  once, judges every address and connects to the judged one: it runs per
  connection, so it covers redirects and pins the address a resolver returned,
  which would also close the DNS-rebinding TOCTOU (SEC-049) in the same place.
  Tracked as the follow-up that folds SEC-049 and these copies together.

### SEC-051: the page-title fetch has no private-range guard

* File: `lib/services/page_title.dart` (`getPageTitle`). Callers:
  `site_editing_controller` (add / auto-name), `edit_site_dialog`,
  `link_controller._executeCreateSite` (an inbound link becomes a new site,
  LIR-009/010), `shortcut_controller`. Found extending the SEC-048/SEC-050
  audit across every page-steerable outbound fetcher.
* Description: `getPageTitle` fetches a user-supplied URL and parses its
  `<title>`. Its own doc names the attacker-reachable source ("the URL can come
  straight from an attacker-authored share intent") and guards the IP leak
  through the proxy seam (LEAK-002), but unlike the four other page-steerable
  fetchers it applies neither the literal guard (`isPrivateOrLoopbackHost`) nor
  the resolving guard (`classifyOutboundTarget`), and it issues the GET with
  `http.Client.get`, which follows redirects. With no proxy, an attacker-supplied
  URL — `http://169.254.169.254/…`, a LAN host, or a public host that
  `302`-redirects to one — is fetched.
* Impact: the GET lands on the internal host (blind SSRF; some endpoints act on
  a GET). The fetched page's `<title>` is returned, cached and shown as the
  site/link name, so a titled internal page's title is read back — but only to
  the local user, not to the attacker who supplied the URL (the attacker does not
  see the screen). For the add / inbound-link callers the URL is also about to be
  loaded as a site, so the fetch is not always a reach beyond what the user's
  action already causes; the sharpest residual is the pre-commit title preview of
  an attacker-supplied URL with no proxy. Gated on a user acting on an external
  URL, so Low.
* Fix (design pending): the other fetchers block private ranges outright, but
  here the URL is often the site's *own* origin — a user adding
  `http://192.168.1.1/` as a site legitimately wants its title — so a blanket
  block would break LAN-site auto-naming, the same tension `icon_service`
  resolves with a `documentHost` allowance. Options:
  - (a) thread the trusted origin from the user-typed callers (add / edit /
    shortcut) so only that host is exempt, guarding the inbound-link and
    share-intent paths;
  - (b) block private ranges in `getPageTitle` outright and let a LAN site be
    named by hand;
  - (c) follow redirects by hand with a per-hop re-check regardless — a redirect
    target is never the URL the user chose, so guarding it costs nothing
    legitimate, and this closes the redirect half with no UX change.
  Recommended: (c) now (zero UX cost, parity with the icon and media fetchers)
  plus (a) for the first-hop literal/resolving guard. The (a)-vs-(b) UX call is
  the maintainer's.

## Note on scope

"Secure" is not a state this review certifies. A pass here is evidence against
what was examined, as [README.md](README.md) and [lab.md](lab.md) say. The
policy proves 9 of 29 of its own requirements by a model, a type or an analyzer
rule and owes the rest in `policy_debt.tsv`; this review records what the audit
of the bridge and the dependencies found, not an absence of other findings.
